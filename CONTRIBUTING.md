# Contributing to MeritPay Contracts

Thanks for your interest in contributing! MeritPay is a zero-knowledge payroll
system on Stellar Soroban. This repository holds the **Circom circuits** and the
**Soroban smart contracts** — the on-chain half of the system. The Next.js
frontend lives in a separate repository.

This document explains how to set up your environment, the standards we hold code
to, and how to get a change merged.

## Ways to contribute

- **Pick up an existing issue.** The [`issues/`](issues/) directory contains a
  curated backlog of well-scoped work items (security hardening, test coverage,
  circuit fixes, tooling). Each file has context, a proposed solution, scope, and
  acceptance criteria. Comment on the corresponding GitHub issue (or open one
  referencing the file) before starting so work isn't duplicated.
- **Report a bug.** Use the bug report issue template. Include the circuit or
  contract involved, the exact commands you ran, and the output.
- **Propose a feature or design change.** Use the feature request template. For
  anything that changes a circuit's public signals, a contract's interface, or
  the trusted-setup process, open the issue for discussion **before** writing
  code — these changes ripple into the frontend and require coordination.
- **Improve docs.** README clarifications, inline doc comments, and examples are
  all welcome.

> **Do not** submit AI-generated bulk PRs, cosmetic churn, or changes with no
> linked issue and no clear rationale. They will be closed.

## Project layout

```
circuits/            Circom 2.0 sources (kpi, payroll_aggregator, claim, auditor_disclosure)
contracts/           Rust workspace, compiled to wasm32v1-none
  groth16_verifier/  Generic BN254 Groth16 verifier
  payroll/           Payroll pool: batch execute, nullifier tracking, escrow
  claim/             Employee claim: individual payout, anti-double-claim
scripts/             setup.sh, deploy.sh, gen_proof.js, upload_vk.js
build/               Generated artefacts — gitignored, regenerated by setup.sh
issues/              Curated contributor backlog (one Markdown file per task)
```

See [`README.md`](README.md) for the protocol design and the two-step payroll
flow.

## Development environment

| Tool | Version | Purpose |
|---|---|---|
| Rust | stable (see `rust-toolchain.toml` if present, otherwise latest stable) | Contracts |
| `wasm32v1-none` target | — | `rustup target add wasm32v1-none` |
| Stellar CLI (`stellar`) | latest | Deploy, key management |
| Node.js | 18+ | Circuit tooling, scripts |
| circom | 2.x | Circuit compilation (`cargo install circom`) |
| `wasm-opt` (binaryen) | optional | Smaller contract wasm |

One-time setup:

```bash
rustup target add wasm32v1-none
cd circuits && npm install && cd ..
./scripts/setup.sh          # compiles circuits + runs the demo trusted setup
```

`setup.sh` downloads two Powers-of-Tau files (~54 MB + ~220 MB). After the first
run, use `SKIP_PTAU=1 ./scripts/setup.sh` to skip re-downloading them.

```bash
# Contracts (all three, release wasm)

# Contracts (native, for tests)

# Circuits

```

## Testing

Every change that touches a contract or circuit **must** come with tests, and the
full suite must pass locally before you open a PR.

```bash
# Contract unit tests
cargo test --workspace

# or per package
cargo test -p meritpay-payroll
cargo test -p claim
cargo test -p groth16-verifier

# Circuit proof generation smoke test (requires ./scripts/setup.sh first)
node scripts/gen_proof.js
```

Contract tests run fully offline using `soroban_sdk::testutils`, mock verifier
contracts (`MockOk` / `MockFail`), and a mock SEP-41 token — no testnet
connection or real proof required.

If your change updates a contract interface, regenerate the test snapshots that
live under `contracts/*/test_snapshots/` (they are produced by `cargo test`) and
commit them.

## Coding standards

### Rust

- `cargo fmt --all` before every commit. CI enforces `cargo fmt --all --check`.
- `cargo clippy --workspace --all-targets` must be clean. Fix warnings; do not
  `#[allow(...)]` without a comment explaining why.
- No new `.unwrap()` / `.expect()` / `panic!` on any code path reachable from a
  contract entrypoint. Return a typed `contracterror` variant instead. (A prior
  audit removed these — keep them out.)
- Follow checks → effects → interactions ordering: validate, then write storage,
  then make external / token calls.
- Every new entrypoint gets a doc comment describing access control, parameters,
  and the errors it can return. Keep the tables in `README.md` in sync.
- Emit an event for every state mutation.

### Circom

- `pragma circom 2.0.0;`.
- Range-check every signal that flows into a comparator (`LessThan` / `LessEqThan`
  are only sound for in-range inputs) or into a division hint.
- Declare all signals and components at template scope (Circom 2.0 requirement
  inside loops).
- Document the full ordered list of public signals in a comment above
  `component main` and mirror it in `README.md`. Contracts index public signals
  positionally — a reordering is a breaking change.
- Any circuit change invalidates the committed trusted setup. Note in your PR
  that `./scripts/setup.sh` must be re-run and coordinate a new ceremony /
  VK upload.

### Shell scripts

- `set -euo pipefail`.
- Pass `shellcheck` cleanly.

## Working with circuits

Because circuits are the real security boundary of this system, circuit PRs get
extra scrutiny:

1. State the soundness property you are preserving or adding.
2. Add positive **and** negative tests (a witness that should be rejected must be
   shown to be rejected). See [`issues/14-circuit-test-suite.md`](issues/14-circuit-test-suite.md).
3. Report the constraint count before/after (`snarkjs r1cs info`). If a circuit
   crosses a Powers-of-Tau size boundary, update `scripts/setup.sh`.
4. Never change the number, order, or meaning of public signals without a linked
   design issue and a note to frontend maintainers.

---

## Working with contracts

1. Keep the `groth16_verifier` wire format (byte offsets, big-endian encoding, G2
   limb order) identical unless the PR is specifically about that format — and if
   it is, update `scripts/upload_vk.js` in the same PR.
2. New storage keys: document them in the contract's storage-layout table and
   consider TTL implications (see
   [`issues/11-persistent-storage-ttl-management.md`](issues/11-persistent-storage-ttl-management.md)).
3. Interface changes must update: the contract, its tests, the test snapshots,
   `scripts/deploy.sh`, and `README.md`.
4. Run `./scripts/deploy.sh` against testnet for anything that changes
   deployment, initialization, or wiring, and paste the result in the PR.

## Commit and branch conventions

- Branch from `main`. Name branches `type/short-description`, e.g.
  `fix/claim-cei-ordering` or `test/verifier-fixtures`.
- Use [Conventional Commits](https://www.conventionalcommits.org/):
  `type(scope): summary`, e.g.
  - `fix(claim): mark nullifier claimed before token transfer`
  - `test(payroll): cover insufficient-funds rejection`
  - `docs(readme): correct verifier count`
  - Types used here: `feat`, `fix`, `docs`, `test`, `chore`, `refactor`,
    `security`, `ci`.
- Keep commits focused and buildable. Squash fixup commits before review.
- Do not add tool/agent attribution lines or co-author trailers to commits.

## Pull request process

1. Open or claim an issue first (except for trivial doc typos).
2. Fill in the pull request template completely, including the **Test plan** and
   the acceptance criteria from the linked issue.
3. Ensure CI is green: `cargo fmt --check`, `cargo clippy`, `cargo test`,
   wasm build, `shellcheck`, and the circuit job.
4. Update `CHANGELOG.md` under `## [Unreleased]`.
5. Keep the PR scoped to one issue. Split unrelated changes.
6. A maintainer will review. Address feedback with additional commits (don't
   force-push mid-review); squash on merge.
7. Breaking changes (circuit public signals, contract interfaces, trusted setup)
   require sign-off from a maintainer **and** confirmation that the frontend repo
   has a tracking issue.

## Security issues

**Do not open a public issue or PR for a vulnerability.** Follow
[`SECURITY.md`](SECURITY.md) for private disclosure. This includes soundness
bugs in circuits, proof-forgery vectors, authorization bypasses, and fund-loss
paths.
